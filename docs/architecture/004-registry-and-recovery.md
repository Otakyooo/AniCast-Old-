# ADR 004: сборки в CI и проверяемое восстановление

Дата: 09.09.2026. Статус: принято и внедрено.

## Решение

GitHub Actions проверяет backend, frontend и инфраструктуру до публикации обоих
образов в GHCR. Для main/tag используется reusable CI, чтобы публикация не могла
обойти проверки. Права packages:write есть только у двух publishing jobs.
Production SSH-ключей и runtime env в GitHub Actions нет.

Релиз — пара образов linux/amd64 с полными registry digest и Git SHA. Artifact
`release-<sha>` содержит mainserver.env, vps.env и release.json без секретов.
Deployment operator добавляет абсолютный ANICAST_ENV_FILE, указывающий на
неизменяемый приватный снимок настроек. Сначала выкладывается MainServer,
затем VPS; проверки и автоматический откат остаются на стороне хостов.
Скрипт тянет только образ приложения, не обновляет попутно PostgreSQL/Redis/Caddy.

Базовые Python/Node образы приложения закреплены по digest. Это сохраняет
воспроизводимость выкладки уже опубликованного образа; apt-пакеты и runner
пока не закреплены полностью, поэтому побитово одинаковая пересборка не обещается.
Обновления базовых образов должны проходить обычные проверки и новый релиз.

## Слабый VPS

На production нет сборок Node/Python. Существующие лимиты frontend 512 MiB,
heap 320 MiB сохранены. Дополнительных постоянных сервисов этот этап не добавляет.

VPS использован только для ограниченной репетиции восстановления вне MainServer.
Это не перенос production API/БД на машину с 1 GiB RAM и не резервный кластер.
Утилита требует заранее загруженные immutable images и минимум 448 MiB
MemAvailable. Распаковщик работает отдельно с 128 MiB; затем PostgreSQL с
192 MiB и API smoke с 160 MiB. Каждый ограничен 0.4 CPU и не может использовать
swap сверх своего memory limit. Если порог не пройден, запуск прекращается.

## Границы репетиции

Копии DB/media скачиваются из зашифрованного внешнего хранилища. Restore получает
случайные имена контейнеров/volumes и закрытую Docker internal network, не
публикует порты и не использует production volumes или секреты. PostgreSQL
восстанавливается в новую БД; API проверяется ролью только с SELECT. У API
локальные временные caches; workers не запускаются, почта отключена.

Media извлекаются потоково в отдельный пустой volume с ограничениями количества,
размера и формата файлов; ссылки и выход пути за volume запрещены. Затем volume
доступен API только для чтения. Созданные ресурсы удаляются после проверки.
Оставшиеся входные дампы содержат личные данные и хранятся приватно до удаления.

Проверка подтверждает восстановление схемы, API каталога, библиотеки, истории и
выдачи постера. Она не проверяет реальные пароли, отправку уведомлений, внешние
видеопровайдеры, переключение DNS или работу при реальном отказе MainServer.
Время restore не равно полному RTO: загрузка копий, образов, конфигурация нового
хоста и переключение трафика измеряются отдельно.

## Откат и дальнейшие ограничения

Сохранены прежние локальные образы и manifest previous.env. Rollback распознаёт
локальный SHA и проверяет его наличие без pull из реестра. Он не откатывает БД
или Compose topology; миграции по-прежнему должны быть expand/contract.

MainServer остаётся единой точкой отказа. До постоянного переноса данных нужен
отдельный ресурсный бюджет, RPO/RTO и репетиция полного переключения. Credentials
доступа к backup, ключи rclone crypt, DNS и runtime env должны иметь отдельный
проверенный путь восстановления: скачивание файлов при доступном MainServer
само по себе этого не доказывает.
