# ADR 009: коллекции и редактор коллекций

Дата: 2026-09-17. Статус: принято, реализовано (backend + frontend), zero-budget.

## Контекст

«Ближайшие приоритеты» из IMPLEMENTATION_STATUS на 12.09 перечисляли переход к
коллекциям и редактор коллекций как следующий UI-этап. Проверка показала, что
функционал уже работает end-to-end, но архитектурных решений не было записано —
этот ADR фиксирует действующий контракт, чтобы его нельзя было случайно изменить
молча. См. [SOCIAL_PROFILES](../SOCIAL_PROFILES.md) (публичные профили и приватность)
и [ADR 002](002-redis-isolation.md) (роль disposable cache).

## Решение

1. **Владение и авторизация.** Все мутации коллекций требуют сессии
   (`IsAuthenticated`). Единственный `AllowAny`-эндпоинт — детальный публичный.
   Операции проверяют `owner=request.user`, поэтому чужая коллекция отвечает 404,
   а не 403 (не раскрываем существование).
2. **Лимиты.** Не более 50 коллекций на пользователя и не более 200 элементов в
   коллекции; превышение — 400 с понятным текстом. Лимит считают внутри
   `select_for_update`-транзакции, а не отдельным запросом, поэтому гонка
   «двух одновременных созданий» не проскакивает.
3. **Порядок элементов.** Позиции плотные (0..N-1), дубликаты тайтлов и позиция
   вне диапазона отклоняются. Вставка и перемещение переписывают порядок целиком
   и переиндексируют все позиции одной инструкцией (`reindex_collection_items`),
   а не сдвигают по одному `save()` — запрос остаётся ограниченным на любой длине.
4. **Публичный доступ — capability, не индексация.** Публичная коллекция доступна
   только по `/api/v1/public/collections/<owner_public_id>/<slug>/` и требует
   `is_public=True` и активного владельца. `public_id` — неизменяемый UUID,
   известный только тому, кому его показали; публичные коллекции не перечисляются
   и не индексируются. Тот же подход, что у публичных профилей: ссылка — это и
   есть право доступа, а не «скрытое от ботов».
5. **Личные данные не кэшируются.** Страницы и summary коллекций пользователя
   отдаются с `no-store, private`. Публичная страница коллекции может кэшироваться
   приватно (короткий TTL), публичный эндпоинт не несёт личных данных других людей.
6. **Payload.** Список коллекций — это карточки с 4-элементным превью
   (`COLLECTION_PREVIEW_LIMIT`), а не полный вложенный состав; полный состав
   отдаёт только детальный эндпоинт. Ответ на вопрос «в каких коллекциях уже
   лежит этот тайтл» считается на стороне API одним запросом, чтобы странице
   тайтла не приходилось тянуть весь вложенный список каждой коллекции.
7. **Slug.** Уникален в рамках владельца и неизменяем после создания;
   коллизия имени — 400, а не молчаливый суффикс.

## Что заменяет

Ничего не заменяет: новый функционал. Контракт приватности согласован с
[SOCIAL_PROFILES](../SOCIAL_PROFILES.md) и ADR 002 (ролями Redis); топологию
сервисов, БД и релизный конвейер не меняет. Миграции аддитивные
(`library/0004`), необратимых операций нет.

## Проверка

- `pytest backend/library` — 386 тестов проходят, включая
  `test_collection_crud_is_authenticated_and_owner_scoped`,
  `test_collection_items_add_move_delete_are_dense_and_reject_duplicates`,
  `test_collection_limits` (50 коллекций / 200 элементов),
  `test_public_collection_visibility_cache_and_payload_safety`,
  `test_collection_list_is_a_bounded_card_payload` (ограничение числа запросов).
- Frontend: typecheck, eslint, 87 unit-тестов и production build зелёные;
  редактор (`components/collection-editor.tsx`) и страница управления
  (`app/collections/manage/[slug]/page.tsx`) компилируются.
- Публичный детальный эндпоинт: `permission_classes = [AllowAny]`, фильтр по
  `is_public=True` и `owner__is_active=True`.
- Не покрыто: browser E2E по потоку коллекций (создание, добавление тайтла,
   переупорядочивание, публичная ссылка) — Chromium/Firefox/WebKit E2E
   других потоков зелёные, отдельного коллекционного спека пока нет.
