## SSR ленты сообщества и полное покрытие sitemap — 2026-09-03

Две последние SEO-задачи из аудита.

`/community` рендерится на сервере:

- лента приходила клиентским `useEffect`, поэтому crawler получал только placeholder загрузки. Значение шире самой страницы: `/community` — **единственный краулимый путь** к `/users/<public_id>` и `/collections/<owner>/<slug>`, которые объявлены индексируемыми. Без входящих ссылок это были орфаны;
- компонент разделён по границе «нужна ли сессия»: `ReviewFeed` — серверный, публичные рецензии в HTML; `FollowingFeed` — клиентский оверлей, который добавляет табы и ленту подписок и оборачивает серверные children. Гость и зритель без подписок видят публичный список без табов и без layout shift после проверки сессии;
- `getPublicReviewsPage` в `lib/api.ts` идёт через общий `request()`, поэтому работает в SSR (браузерная версия в `lib/community.ts` удалена вместе с заменённым компонентом);
- подтверждено на живом сайте: создал рецензию, одобрил её, HTML содержит `<article>`, текст рецензии, ссылку на `/titles/21-one-piece` и на `/users/<public_id>`; профиль по этой ссылке отвечает 200 с self-canonical. После удаления тестового аккаунта раздел вернулся к empty state.

Sitemap — полное покрытие вместо молчаливой обрезки:

| --- | --- | --- |
| Персонажи | 500 из 7007 | **7007** |
| Франшизы | 0 | 15 (все с >1 тайтлом) |

Причина обрезки — `MAX_PAGES = 25` при 20 записях на страницу. Документ при этом отвечал 200 и выглядел корректным: лимит, который никто не замечает. Записано в backlog `SEO_OPERATIONS.md` вместе с отдельным вопросом: 6221 персонаж из 7007 связан с одним тайтлом и не имеет описания, то есть страница почти не отличается от карточки в списке — порог «есть описание или несколько тайтлов» дал бы 1299 URL, но решать это надо по данным Search Console, а не заранее.

## Telegram-релей и решение по edge-кешу — 2026-09-03

Две задачи, которые раньше были помечены как «требует решения», закрыты.

Telegram-релей:

- `api.telegram.org` недостижим с MainServer (таймаут с хоста, из backend-контейнера и из Alertmanager; с VPS тот же запрос отдаёт 302, Jikan с MainServer доступен). Каддy на VPS теперь отдаёт релей внутри AmneziaWG-туннеля: `MainServer → http://10.78.0.1:8443/bot<token>/<method> → https://api.telegram.org`. Внутренний хоп — plain HTTP, как и обращение к самому backend'у (`10.78.0.2:8000`): туннель уже шифрован, а выпускать сертификат на IP-адрес не за чем. Хоп до Telegram — HTTPS с проверкой по системному store;
- через релей переведены все четыре потребителя: пользовательские уведомления (`TELEGRAM_API_BASE_URL` вместо хардкода в `push/telegram.py`), Alertmanager (`api_url`), и — что обнаружилось по ходу — `scripts/backup-db.sh` и `backup-posters.sh`. Скрипты бэкапа звали Telegram напрямую, то есть падение бэкапа сообщало о себе только в stderr на cron-запуске: алерт отбрасывался ровно тогда, когда был нужен;
- защита релея от превращения в открытый прокси — четыре независимых условия, и **`bind 10.78.0.1` из них главное**. Адрес сайта в Caddy сопоставляется только с заголовком Host, поэтому без `bind` листенер поднимается на `*:8443` — это подтвердилось в проде на первом деплое (`ss -tlnp` показал `*:8443`, и от интернета его отделял только firewall). Плюс `remote_ip 10.78.0.0/24`, `path /bot*`, `method POST GET`. Access-лог на этом сайте отсутствует намеренно: токен бота — часть URL, и лог писал бы живые credentials на диск при каждом уведомлении;
- по ходу исправлено правило `AlertDeliveryFailing`: метрика Alertmanager несёт ещё и label `reason`, поэтому исходное выражение поднимало отдельный алерт на каждую причину сбоя одного канала. Добавлен `sum by (integration)`.

Edge-кеш `/api/v1/media/*` — **решено не делать**, по измерениям:

| Метрика на периметре (окно 56 мин) | Значение |
| --- | --- |
| Доля media в запросах | 16 из 691 |
| Repeat ratio | 1.0 (ни один URL не запрошен дважды) |
| p50 / p95 latency | 0,29 с / 0,55 с |

Кеш, которому нечего отдавать из кеша, стоил бы кастомной сборки Caddy и её supply chain без выигрыша. Django уже отдаёт `immutable`, поэтому повторные визиты браузера бесплатны.

Настоящей причиной трафика на media оказались crawler'ы: **46% запросов периметра** — backlink/keyword-боты (один MJ12bot 35%), и каждый байт постера для них шёл через туннель с MainServer. `robots.txt` теперь закрывает этой группе (MJ12bot, SemrushBot, AhrefsBot, Amazonbot) только путь media — HTML, ссылки и метаданные им по-прежнему доступны, поэтому сайт остаётся видимым в отчётах Ahrefs/Semrush, а поисковики не затронуты вовсе. Проверено на живом сайте: Googlebot получает постер 200, MJ12bot получает `/catalog` 200.

Проверка: backend 307 passed, ruff, mypy (145 файлов) — чисто; frontend 58/58 unit, lint, typecheck, build; `promtool check rules` 18 правил; `caddy validate`; `scripts/validate.sh` пройден. Production: образы `local-20260903T143408Z`, predeploy dump `anicast-20260903T143408Z.dump`, все контейнеры healthy, 5xx после релиза — 0, **firing alerts — 0** (`AlertDeliveryFailing` погас впервые с момента добавления).

Доставка подтверждена на живом стеке: реальное сообщение через релей доставлено (`message_id: 57`), `alertmanager_notifications_failed_total{integration="telegram"}` = 0 при `notifications_total` = 1, `getMe` для `anicast_push_bot` из Celery-воркера отвечает `ok: True`. Релей недоступен с публичного адреса (`89.125.113.33:8443` closed), нецелевые пути отдают 404.

## Публичные данные аккаунтов, enumeration и стоимость дашборда — 2026-09-03

Разбор оставшихся находок аудита по приватности и админке.

Публичные payload'ы:

- из публичных рецензий убран внутренний PK. `display_name or f"AniCast #{obj.user_id}"` подставлял первичный ключ аккаунта, когда имя не задано — то есть раскрывал порядок регистрации и приблизительное число пользователей, причём именно для тех авторов, у кого `public_id` сознательно скрыт. Теперь API возвращает имя как есть (возможно пустое), а плейсхолдер выбирает клиент через существующий ключ `account.viewer`;
- деактивация аккаунта наконец работает как takedown. Она уже скрывала профиль и блокировала подписки, но одобренные рецензии оставались читаемыми на каждой странице тайтла, а публичные коллекции открывались по прямой ссылке. Добавлены `user__is_active` в `published_reviews()` и `owner__is_active` в `PublicCollectionDetailView`.

Enumeration при регистрации:

- регистрация вынесена в отдельный bucket `register=20/hour` на адрес. Login сознательно обезличен, а регистрация обязана сообщить вернувшемуся пользователю, что адрес занят — без верификации по email другого способа нет, поэтому эндпоинт по построению является oracle'ом. Общий с login бюджет `10/min` давал ~14 000 проб в сутки с одного адреса; часовой bucket невидим для человека, регистрирующегося один раз. Настоящее решение — верификация по email («проверьте почту» в обоих случаях), но для этого нужна доставка почты, которой у хоста пока нет;
- при этом обнаружено, что `override_settings` **никогда не влиял** на throttle-лимиты: DRF привязывает `THROTTLE_RATES` к классу на этапе импорта. Тесты, которые «проверяли» изменённый rate, проверяли дефолтный. Добавлен `LiveRatesMixin`, читающий таблицу ставок на каждый инстанс, и применён ко всем AniCast-throttle'ам — теперь лимиты действительно тестируемы.

Cookie:

- `CSRF_COOKIE_HTTPONLY` → `True`. Фронтенд берёт токен из тела `/api/v1/auth/csrf/` (`lib/auth.ts:getCsrfToken`) и нигде не читает `document.cookie` для csrftoken — проверено grep'ом. Доступность cookie для скриптов не давала ничего, кроме бесплатного токена для инъектированного скрипта;
- `SESSION_SAVE_EVERY_REQUEST` оставлен намеренно и задокументирован: он покупает rolling-expiry (активный зритель не разлогинивается, неактивный уходит через 30 дней). Цена — один UPDATE сессии на запрос, что измеримо далеко за пределами текущего трафика. Отключение логаутило бы всех через 30 дней после входа независимо от активности.

Стоимость `/staff/`:

- `summarize()` загружал 7-дневное окно проб в Python: при минутном разрешении это ~13 000 строк на цель и ~39 000 на рендер дашборда, чтобы посчитать проценты. Переписано на bounded-агрегаты (`Count`/`Avg`/`Min`/`Max` с `filter`) — тот же приём, которым уже пользовался Prometheus-путь в том же файле. Измерено на production: дашборд с 0,94 с до **0,065–0,082 с** на прогретом кеше (холодный первый рендер 0,70 с — чтение страниц с диска), запросов 22, и стоимость больше не растёт вместе с историей. Контракт подтверждён существующими тестами без изменений плюс новый бюджет-тест: удвоение истории не меняет число запросов;
- `_poster_tier_counts` **не** менялся: измерено 0,16 с при 2 запросах, и переписывание на 5 unindexed `LIKE`-сканов дублировало бы грамматику имён файлов в SQL ради вероятного замедления.

## Кеширование ответов и доставка изображений — 2026-09-03

Публичные каталожные GET раньше уходили в PostgreSQL на каждый запрос: ни `Cache-Control`, ни `ETag` в проекте не было нигде.

- 13 публичных эндпоинтов (каталог, деталь тайтла, similar, эпизод, watch-navigation, расписание, жанры, франшизы, персонажи, авторы, медиа, поиск) отдают `public, max-age=0, s-maxage=60, stale-while-revalidate=300`; поиск — `s-maxage=300`, поскольку выполняет три неиндексированных ILIKE-скана на запрос. `Vary: Accept, Accept-Language, Cookie` — несущая часть: payload локализуется из `?lang=`, cookie `anicast_lang` и `Accept-Language`, и shared-кеш без этого отдал бы один язык другому посетителю;
- аутентифицированные ответы сознательно не помечаются кешируемыми, playback сохраняет `no-store, private`. Оба случая покрыты тестами: цена ошибки — данные одной сессии в другой;
- `formats: ["image/webp"]` в next config. Без этого Next не согласовывал ничего, и браузер с поддержкой WebP получал исходный PNG/JPEG. AVIF **не включён** намеренно: измерено на production-VPS (1 vCPU) на реальном постере 6,2 МБ при quality 92 — WebP 88,6 КБ за 1,9 с, AVIF 122,1 КБ за 6,8 с. На этом уровне качества AVIF и больше, и в 3,5 раза дороже, а Next согласовывал бы его первым;
- `minimumCacheTTL` 30 дней вместо дефолтных 60 секунд. Имена постеров контент-адресуемые (префикс SHA-256), поэтому URL не меняет смысл и длинный TTL не может отдать устаревшую обложку. Дефолт перекодировал одни и те же постеры весь день; cold miss через туннель стоит до 4 с, hit — около 0,5 с.

**HTTP/3 включить нельзя, и это выяснилось через двухминутную недоступность сайта.** AmneziaWG слушает UDP/443 (`ListenPort = 443` в `awg0.conf`), маскируя туннель под QUIC. h3-листенер Caddy падает с `bind: address already in use`, а Caddy считает это фатальной ошибкой конфигурации: контейнер уходит в restart-loop и вместе с h3 исчезает весь сайт. Откат до `protocols h1 h2` вернул работу; ограничение задокументировано в `docs/OPERATIONS.md` с явным запретом возвращать `h3` без переноса порта туннеля. Судить об этом заранее было можно — `ufw` показывал `443/udp ALLOW`, но не показывал, что порт уже занят; проверять надо было `ss -ulnp`, а не firewall.

Edge-кеш для `/api/v1/media/*` не сделан: у Caddy нет модуля кеша, поэтому это выбор между кастомным образом с `cache-handler` и CDN — решение про сборку и supply chain, а не про конфиг. Django уже отдаёт `immutable`, так что повторные визиты браузера бесплатны; платит только cold request через туннель.

Проверка: backend 299 passed, ruff, mypy (145 файлов) — чисто; frontend 58/58 unit, lint, typecheck, build; `scripts/validate.sh` и `caddy validate` пройдены. Production: образы `local-20260903T000145Z`, predeploy dump `anicast-20260903T000145Z.dump`, все контейнеры healthy, 5xx после релиза — 0, firing alerts — 0, 11 публичных маршрутов 200. Заголовки подтверждены на живом сайте, включая `no-store` на playback и `immutable` на постерах.

## Redis-аутентификация, изоляция мониторинга и алерты на причину — 2026-09-02

Третья часть аудита: закрыты два пути доступа к данным и добавлены алерты на то, что раньше оставалось невидимым.

Redis:

- Redis теперь требует пароль (`REDIS_PASSWORD` → `--requirepass`), пароль присутствует в `CACHE_URL`, `CELERY_BROKER_URL` и `CELERY_RESULT_BACKEND`. Это не defence in depth: Redis держит брокер Celery, имена задач публичны, и кто может писать в брокер — исполняет код в воркере. Неаутентифицированный Redis в общей Docker-сети это путь к RCE, а не кеш. Healthcheck читает `REDISCLI_AUTH` из окружения, поэтому `redis-cli ping` извне контейнера отвечает `NOAUTH Authentication required` — это ожидаемый здоровый ответ.

Изоляция мониторинга:

- `metrics-proxy` вынесен из `mainserver_internal` в новую scrape-only сеть `mainserver_metrics`, где живёт только backend. Раньше monitoring-стек подключался к сети приложения ради одного HTTP-эндпоинта и получал вместе с ней `postgres:5432` и `redis:6379` — оба были подтверждённо достижимы из nginx-контейнера. Docker DNS отвечает в пределах сети, поэтому теперь контейнер не может даже разрешить имена `postgres` и `redis` (проверено: `nc: bad address`, при этом `backend` REACHABLE).

Алерты — на причину, а не на симптом:

- `PendingMigrations` (`anicast_pending_migrations` в `/internal/metrics`). Модель, ссылающаяся на отсутствующие в схеме колонки, отдаёт 500 на каждом запросе, который их читает; именно так пропущенная миграция час оставалась незамеченной — был виден только симптом;
- `EndpointGroupErrorRatio` — доля 5xx по группе эндпоинтов с порогом 20% и минимумом 20 запросов за окно. Абсолютный счётчик срабатывает от объёма: на сайте с малым трафиком одна группа, отдающая 500 на каждый запрос, даёт мало ошибок в минуту. Backtest на инциденте: в пике API-группа шла с **48% ошибок** (72 из 148), при этом суммарный порог в 3 ошибки за 15 минут был превышен лишь эпизодически;
- `AlertDeliveryFailing` — следит за самим каналом доставки. Любое правило бесполезно, если сообщение не приходит.

**Обнаружена нерешённая инфраструктурная проблема.** `api.telegram.org` недостижим с MainServer: timeout с хоста, `Network is unreachable` из backend-контейнера, timeout из Alertmanager. С VPS тот же запрос отдаёт 302 за 0,2 с, а Jikan с MainServer доступен, значит это не DNS (имя резолвится), не маршрут (`via 192.168.0.1` есть) и не общий блок egress. Из четырёх Telegram-IP один принимает TCP, но TLS всё равно не завершается.

Последствия: `alertmanager_notifications_failed_total{integration="telegram"}` = 274 из 274 попыток, 291 запись `notify retry canceled` в логе. При этом `High5xxRate` **сработал корректно** — pending с 17:52 UTC, firing с 17:57 до 19:12; проблема не в правилах, а в доставке. Тот же путь использует `push/telegram.py` для пользовательских уведомлений, поэтому весь Telegram-функционал нерабочий по построению (доставок пока не было — каналов нет, на пользователях не отразилось).

Варианты решения требуют выбора: релей через VPS, другой канал алертов (email/webhook/ntfy), egress-прокси на MainServer или устранение блокировки на уровне сети. Задача зафиксирована в `docs/OPERATIONS.md` как известный gap.

Проверка: backend 285 passed, ruff, mypy (145 файлов) — чисто; `promtool check rules` — 18 правил; `scripts/validate.sh` пройден. Production rollout: образ `anicast-backend:local-20260902T215253Z`, predeploy dump `backups/db/anicast-20260902T215339Z.dump`, все контейнеры healthy, 5xx после релиза — 0, ошибок аутентификации Redis в логах backend и worker — 0, `anicast_pending_migrations` = 0 в Prometheus, три новых правила `health=ok state=inactive`, 11 публичных маршрутов 200.

## Границы ответов и индексы — 2026-09-02

Вторая часть аудита: устранены ответы, размер которых зависел от объёма данных пользователя, и добавлены индексы под фактические filter+order паттерны.

Границы ответов:

- `DEFAULT_PAGINATION_CLASS` и `PAGE_SIZE` заданы в DRF. ## Лимиты API, SEO-регрессии и N+1 — 2026-09-02

Аудит проекта (уязвимости, производительность, SEO, мусор) выявил набор дефектов, которые исправлены одним релизом.

Безопасность и зависимости:

- сравнение всех header-секретов вынесено в `common.security.constant_time_equals`. Django декодирует заголовки как latin-1, а `hmac.compare_digest` бросает `TypeError` на не-ASCII `str`, поэтому один заголовок `X-AniCast-Internal-Token` из символов U+0080–U+00FF превращал дефолтный throttle в неаутентифицированный 500 на **любом** API-запросе. - из проверки placeholder-`SECRET_KEY` убрано условие `not DEBUG`: стек, случайно поднятый с `DJANGO_DEBUG=1`, иначе подписывал бы сессии, visit-cookie и playback-токены публично известным ключом;
- добавлен `AniCastUserRateThrottle` (`user=240/min`). DRF `AnonRateThrottle` возвращает `None` для аутентифицированных запросов, поэтому один дешёвый аккаунт мог без лимита нагружать `/account/summary/`, `/recommendations/` и `/continue-watching/`;

## Рекомендации: причины, честный скоринг и «Не интересно» — 2026-08-26

- выдача `/api/v1/recommendations/` получила машиночитаемые причины: каждый результат несёт `reasons: {genres: [...], franchise: bool}` — топ-3 совпавших позитивных жанров в локализации запроса (через существующий переводной механизм) и флаг франшизы; поле аддитивно, старые клиенты совместимы;

## Providers и права

- добавлен provider registry с enabled-флагом и allowlist HTTPS-хостов;
- существующие источники мигрируются к disabled providers без автоматического права просмотра;
- прямой `Source.url` удалён из всех публичных serializers;
- rights grant привязан к конкретному источнику, имеет обязательный интервал и contract reference;
- одновременно допускается только один active grant на источник;
- playback endpoint работает fail closed и повторно проверяет provider, availability, approved grant, срок и hostname;
- provider явно выбирает зарегистрированный playback adapter; отсутствующий или неизвестный adapter закрывает playback;
- нейтральный `external_link` adapter не имитирует API поставщика и не принимает credentials/config;
- API сохраняет контракт `mode + url`, но выдаёт подписанный внутренний URL с TTL 60 секунд вместо постоянного `Source.url`;
- при открытии короткоживущего URL заново проверяются source, enabled provider, adapter и active approved grant;
- token не содержит target URL или credentials, а redirect разрешён только на точный HTTPS hostname из allowlist;
- playback и redirect responses имеют `no-store`, redirect также запрещает передачу referrer;
- activation и revocation выполняются audited admin actions;
- admin и import отклоняют неизвестные adapters, credential config, private/reserved IP hosts и source URL вне allowlist;
- frontend показывает «Открыть у провайдера» только при `playback_available=true` и принимает только same-origin playback URL.

## Мониторинг источников

- Celery Beat проверяет enabled provider sources каждые 10 минут;
- URL обязан быть HTTPS, входить в provider allowlist и резолвиться только в public global IP;
- private/reserved адреса и redirects отклоняются до изменения состояния;
- сохраняются HTTP status, latency, безопасный bounded error code и история проверок;
- после трёх последовательных сбоев выставляется `provider_error` и playback немедленно закрывается;
- успешная проверка восстанавливает только автоматически выставленный `provider_error`;
- ручные `unavailable`, `geo_blocked` и `expired` мониторинг не перезаписывает;
- диагностика и история доступны в `/staff/`.

## Постеры: тир `o` — записанный original как источник апгрейда

- пайплайн хранит приватный `poster_origin_url` (upstream original, обычно 1000–3000 px); записанный origin служит источником серверного апгрейда, но никогда не сериализуется наружу — тир `o` (`-o-` в имени файла, regex `[mlsko]`);
- origin-проба вставлена после ветки Jikan-maximum и перед логикой large/kitsu: максимум MAL по-прежнему забирается без лишней загрузки, а провал origin (error/invalid/current) не блокирует остальные источники; кандидат принимается только через `_adopt_if_larger` — строго больше хранимого файла по площади;
- пробуются только origins, записанные до текущего обновления: строка с только что реконструированным `_ensure_origin` origin сначала проходит обычный апгрейд и становится кандидатом `o` со следующего цикла; сырые хотлинки по-прежнему дешевле зеркалируются как `s`;
- сравнение Jikan-large с хранимыми `l`/`k` файлами обобщено на пиксели: деградировавший малый `l`-файл теперь самолечится;
- исход метрики `anicast_poster_refresh_total{result="original"}`; очередь не менялась (тир `o` в bucket 2 рядом с `l`/`k`); миграций нет;
- тесты: обновлён `test_adopt_records_remote_origin` (восстановление после потери файла теперь строже — из origin как `o`, а не mirror `s`) + 4 новых кейса (апгрейд s→o, отказ от меньшего origin с провалом в large, bucket приоритета, regex).

## Сетевая оптимизация и доступность в админке (2026-08-25)

### Маршрутизация и кэш фронтенда

- SSR-фетчи Next.js больше не ходят по кругу «VPS → интернет → Caddy → туннель»: серверные вызовы идут напрямую через AWG на `INTERNAL_API_BASE_URL=http://10.78.0.2:8000/api/v1` с заголовком `X-Forwarded-Proto: https` (тот же trust domain, что у ноги Caddy→backend); клиентский бандл внутренний адрес не содержит (проверено по чанкам);
- замер на VPS: titles API через публичный край 315–335 мс, напрямую по туннелю 116–159 мс (~2.2×); рендер страницы тайтла 0.70 с → 0.29–0.34 с;
- горячие публичные GET переведены с `no-store` на Data Cache: каталог/тайтл/расписание 60 c, франшизы/персонажи/медиа/similar 300 c; поиск, episode detail API и playback остались без кэша (свежесть токенов и выдачи);
- sitemap.xml получил TTL-кэш 10 минут со stale-fallback: повторный запрос 0.12 с вместо 4.7–5.7 с (раньше каждый запрос кроулил до 25 страниц API);
- компрессия уже обеспечена Caddy (zstd/gzip) для HTML и JSON — изменений не требовалось.

### Тюнинг ядра обеих машин

- MainServer и VPS: `/etc/sysctl.d/99-anicast-network.conf` — `tcp_congestion_control=bbr`, `default_qdisc=fq`, буферы автотюнинга до 16/32 МиБ (у VPS были дефолтные 208 КиБ), `tcp_fastopen=3`;

## SEO-пакет

Актуальная политика индексирования и релизный gate — `docs/SEO_OPERATIONS.md`. Ниже фиксируется только состояние реализации.

- `/robots.txt`: публичные разделы открыты, служебные пути (`/api/`, `/staff`) закрыты, публичные медиа `/api/v1/media/` открыты явным `Allow` (постеры публикуются как `og:image` и JSON-LD `image`), указана ссылка на sitemap. Личные HTML-зоны закрываются не `robots.txt`, а заголовком `X-Robots-Tag: noindex, follow` из `next.config.ts` — иначе crawler не смог бы прочитать директиву и удалить URL из индекса;
- `/sitemap.xml` рендерится на каждый запрос: статические маршруты плюс тайтлы и персонажи из API (обход пагинации до 25 страниц, устойчив к любому размеру страницы бэкенда); при недоступном API деградирует до статических маршрутов вместо ошибки. Франшизы, авторы, публичные коллекции и профили пока не входят, персонажи ограничены лимитом обхода — см. backlog в `SEO_OPERATIONS.md`;
- корневой `generateMetadata` получил `metadataBase` от `NEXT_PUBLIC_SITE_URL`, дефолтную OG-карточку `public/og.png` (1200×630, токены дизайна) и Twitter card;
- страница тайтла: локализованные title/description из синопсиса, canonical, OG/Twitter с абсолютным URL постера, JSON-LD `TVSeries` (name, alternateName, описание, жанры, год, число эпизодов). `aggregateRating` публикуется через `titleRating`, то есть при том же пороге голосов, при котором рейтинг виден на странице;
- страницы франшиз (индекс и деталь), персонажа, автора, публичной коллекции, каталога и расписания имеют собственные canonical + OG метаданные; поиск франшиз консолидируется на `/franchises` как `noindex, follow`;
- degraded-рендер публичных страниц (API недоступен, HTTP 200 с оболочкой «сайт недоступен») отдаёт `noindex, follow`, чтобы заглушка не заменила настоящую страницу в индексе;
- JSON-LD сериализуется через `lib/seo.ts:jsonLdScript`, который экранирует `<` и разделители строк: значения приходят из внешнего импортёра;

## Ограничения

- точная позиция просмотра не реализована без доверенного callback от провайдера;
- источники не запускаются, пока не определены права и разрешённый способ интеграции;
- Telegram bot token и webhook secret должны храниться только в игнорируемом production `.env`;
- для первого входа в `/staff/` требуется отдельно создать superuser с сильным уникальным паролем;
- test suite использует SQLite, а критический Telegram polling flow дополнительно проверяется production smoke-тестом на PostgreSQL.
- metrics counters хранятся в Redis и могут сброситься при потере Redis; endpoint не заменяет внешний alert evaluator;
- автоматический rollback откатывает только application images и требует backward-compatible expand/contract migrations; restore PostgreSQL — осознанная ручная операция по runbook из OPERATIONS.md (автоматизируемая проверка scratch-реставрацией включена в cron);
- rclone на MainServer использует shared client_id Google Drive — пошаговый ранбук миграции на project-owned OAuth client готов в OPERATIONS.md, миграцию нужно выполнить на хосте;
- формальный пайплайн `deploy.sh` в production ещё не выполнялся: репетиционный чеклист готов (OPERATIONS.md), скрипты принимают `ANICAST_PROJECT_MAINSERVER`/`ANICAST_PROJECT_VPS` для работы под живыми именами compose-проектов `mainserver`/`vps` — без переопределения первый прогон создал бы параллельные стеки с пустыми volume'ами; hermetic-тест покрывает и rollback-, и happy-path-ветку деплоя.
