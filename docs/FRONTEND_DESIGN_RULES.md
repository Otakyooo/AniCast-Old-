# AniCast — правила проектирования интерфейса

Версия: 1.0  
Дата: 29 августа 2026

## Назначение

Этот документ задаёт единые правила для создания, изменения и ревью
пользовательского интерфейса AniCast. Он применяется к `frontend/app/`,
`frontend/components/` и связанным пользовательским сценариям API.

Источники истины используются в таком порядке:

1. требования текущей задачи;
2. продуктовые и эксплуатационные документы в `docs/`;
3. бренд и токены из `docs/BRAND_UI_TECH_SPEC.md` и
   `frontend/app/theme.css`;
4. существующий компонент или сценарий, уже решающий ту же задачу;
5. эти правила.

Если источники противоречат друг другу, не маскировать конфликт новой локальной
договорённостью: сохранить безопасное текущее поведение и явно описать, что
требует решения.

## Перед изменением

- Найти ближайший аналог экрана, компонента и API-flow в проекте.
- Определить основную задачу пользователя и одно главное действие в текущем
  контексте.
- Перечислить состояния данных и взаимодействия, затронутые изменением.
- Проверить русский и английский варианты текста, длинные названия и отсутствие
  данных.
- Не устанавливать UI-библиотеки и не менять систему стилизации без отдельного
  решения пользователя.

Наличие старого нарушения этих правил не разрешает распространять его на новый
код и не означает разрешения на массовый рефакторинг. Исправлять соседний код
только тогда, когда это необходимо для целостного и проверяемого изменения.

## Информационная архитектура

- Группировать страницы и действия по пользовательским сущностям AniCast:
  тайтлы, эпизоды, библиотека, история, коллекции, рекомендации, персонажи и
  авторы.
- Сохранять названия сущностей одинаковыми в навигации, заголовках, кнопках и
  сообщениях.
- Не добавлять новый пункт верхнего уровня, если задача помещается в существующий
  раздел.
- Показывать текущее местоположение активным состоянием навигации; на глубоких
  страницах использовать понятный возврат или breadcrumbs.
- Основной контент должен идти раньше вспомогательных панелей и сохранять
  логичный порядок чтения в DOM.
- Редкие и расширенные настройки раскрывать по запросу пользователя, но не
  прятать обязательные условия и частые действия.

## Компоновка и адаптивность

- Использовать `PageShell` и существующие общие каркасы вместо дублирования
  header, footer, content width и back-navigation.
- Для структуры предпочитать grid/flex и содержательные группы; не выравнивать
  блоки случайными отступами.
- Внутри компонента расстояния должны быть меньше, чем между самостоятельными
  секциями.
- Переиспользовать ближайший установленный breakpoint. Новый breakpoint допустим,
  только если его требует поведение контента, а не конкретная модель устройства.
- На узком экране сохранять главное действие, порядок чтения и доступ к данным;
  горизонтальный скролл допустим только для форматов, где он является частью
  взаимодействия.
- Проверять как минимум узкий мобильный, промежуточный и широкий desktop viewport.
- Не обрезать важные названия или сообщения без доступного способа увидеть полный
  текст.

## Визуальный язык

- Цвета брать только из семантических CSS variables, зафиксированных в
  `BRAND_UI_TECH_SPEC.md` и `globals.css`.
- Не добавлять необоснованные hex/rgba, декоративные градиенты, новый шрифт,
  семейство иконок или уникальную тень для одного компонента.
- Использовать Phosphor Icons для новых интерфейсных иконок. Иконка дополняет
  понятную подпись; без текста она допустима только при однозначном смысле и
  доступном имени.
- Сохранять различие primary, secondary и destructive действий не только цветом,
  но также подписью, положением и визуальным весом.
- Новые значения spacing, typography, radius и motion сначала оформлять как
  переиспользуемый token, если они нужны более чем в одном месте.
- Анимация должна объяснять изменение состояния. Учитывать
  `prefers-reduced-motion` и не делать движение условием понимания интерфейса.

## Компоненты и состояния

Каждый интерактивный компонент должен иметь применимые к нему состояния:

- default;
- hover и `focus-visible`;
- active/pressed или selected;
- disabled, если действие может стать недоступным;
- pending/loading для асинхронного действия;
- success только после подтверждения backend;
- error с понятным восстановлением.

Компоненты, зависящие от данных, дополнительно проектируются для initial loading,
empty, partial data, unavailable и retry. Не заменять содержательную ошибку
безадресным toast, если проблема относится к конкретному полю, карточке или
секции.

- Использовать native element (`button`, `a`, `input`, `select`) до создания
  собственного интерактивного примитива.
- Не превращать контейнер в кликабельный через обработчик без корректной
  клавиатурной и семантической модели.
- У компонента должно быть одно главное действие; вторичные и опасные действия
  не должны конкурировать с ним.
- Для повторяющегося паттерна сначала проверить `frontend/components/`, затем
  расширить общий компонент или создать новый с ясным контрактом.

## Асинхронные сценарии и честность данных

- Показывать feedback рядом с областью, которая меняется.
- Не очищать полезные данные во время фонового обновления, если их можно безопасно
  оставить видимыми.
- Не сообщать об успехе до успешного ответа API и не скрывать частичный результат
  как полный.
- Ошибка объясняет, что не выполнено, что сохранено и какое действие доступно
  дальше.
- Повторная отправка не должна незаметно дублировать мутацию; pending-state должен
  блокировать только конфликтующие действия.
- При временной недоступности API сохранять спокойный тон и путь к повторной
  попытке. Не выдавать инфраструктурные детали пользователю.
- Учитывать stale responses, быстрые повторные действия и смену маршрута во время
  запроса.

## Формы

- Всегда связывать label с полем; placeholder не заменяет label.
- Обязательные требования сообщать до отправки, а не только после ошибки.
- Ошибку поля размещать рядом с ним и связывать через доступное описание.
- Cross-field и серверные ошибки показывать в контексте формы, сохраняя введённые
  пользователем значения.
- Кнопка отправки должна называть действие. Не использовать `OK` или `Submit`,
  когда можно написать результат: «Сохранить профиль», «Создать коллекцию».
- После ошибки переводить фокус только тогда, когда это помогает восстановлению;
  не перехватывать его неожиданно.
- Опасное или необратимое действие требует ясного последствия и подтверждения,
  соразмерного риску.

## Доступность

- Цель — WCAG AA или выше согласно `BRAND_UI_TECH_SPEC.md`.
- Весь основной flow должен проходиться клавиатурой в логичном порядке с видимым
  фокусом и без ловушек.
- Заголовки и landmarks должны отражать реальную структуру страницы.
- ARIA использовать для дополнения, а не замены нативной семантики.
- При открытии dialog/overlay переводить фокус внутрь, удерживать его в пределах
  модального контекста и возвращать инициатору после закрытия.
- Изменения статуса, которые не получают фокус, объявлять assistive technologies,
  когда без этого результат действия останется незаметным.
- Не передавать ошибку, выбор или доступность только цветом.
- Информативные изображения получают содержательный alt; декоративные исключаются
  из accessibility tree.

Автоматическая accessibility-проверка является только одним уровнем контроля и
не заменяет keyboard и screen-reader review.

## Текст интерфейса

- Писать коротко, прямо и без внутренних терминов backend или провайдера.
- Название действия описывает ожидаемый результат.
- Success сообщает, что изменилось; error — что не получилось и как продолжить.
- Тон AniCast спокойный и человеческий. Не использовать шутку там, где пользователь
  потерял данные, доступ или возможность просмотра.
- Новая пользовательская строка должна проходить через существующую i18n-систему,
  если экран уже локализован. Не смешивать языки внутри одного flow.
- Текст должен выдерживать более длинный перевод без разрушения layout.

## Next.js и границы компонентов

- Сохранять App Router и Server Components по умолчанию.
- Добавлять `use client` только для browser API, локального интерактивного состояния
  или event handlers; не переносить туда загрузку данных без причины.
- Route-specific UI размещать рядом с route, переиспользуемый — в
  `frontend/components`, работу с данными и преобразования — в `frontend/lib`.
- Не помещать бизнес-правила в JSX и CSS.
- Для image/media использовать существующую стратегию постеров и fallback; не
  подменять отсутствие реального изображения декоративной генерацией без явного
  продуктового решения.

## Definition of done

Для пользовательского изменения проверить:

1. основной flow и хотя бы один отказ или пустое состояние;
2. default, focus, pending и error состояния затронутых контролов;
3. keyboard-only прохождение и доступные имена;
4. узкий mobile и широкий desktop layout;
5. соответствие цветам и токенам AniCast;
6. русский и английский текст, если flow локализован;
7. отсутствие ложного success и потери введённых данных;
8. `npm run lint`, `npm run typecheck`, `npm test`, `npm run build` из
   `frontend/`.

Если browser-level или screen-reader проверка недоступна, это указывается в итогах,
а не считается автоматически пройденным gate.
