# Transitive dependency pins.
#
# Generated from the exact set installed by the production image, so an install
# resolves to the versions that were actually tested. Direct dependencies stay in
# requirements.txt; only what they pull in belongs here.
#
# The pins exist for reproducibility, not for the audit: pip-audit already walks
# the resolved dependency graph rather than only the named pins (verified — one
# `requests==2.34.2` line audits urllib3, idna, certifi and charset-normalizer
# too). What was missing before was determinism: an empty constraints file let a
# rebuild pick up any newer transitive release, so an image built today could
# differ from the one the test suite passed on.
#
# Regenerate after changing requirements-prod.txt, from a freshly built image:
#
#   docker exec mainserver-backend-1 pip freeze
#
# and keep only the entries that are not in requirements-prod.txt. Pinning a package
# that is also a direct dependency would make the two files disagree, and pip
# resolves the conflict in favour of the constraint.
